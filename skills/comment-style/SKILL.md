# comment-style

One pattern, adapts everywhere. Deterministic: same situation, same comment - if
two reviewers would write different comments for the same code, at least one is
violating a rule.

## Precedence - what governs

1. The project's own documentation rules (its AGENTS.md/CLAUDE.md, style guide,
   rules files) win wherever they speak.
2. The language/stack's canonical doc syntax (TSDoc/JSDoc, docstrings, godoc,
   rustdoc, `#` comments) decides expression only - same decisions, native form.
3. This pattern fills what is still undefined.

Does not apply to files another tool or an upstream owns: "installed by",
"managed by", "generated by", `@generated`, vendored code. Their comments stay
untouched; fix the generator or upstream, not the file.

## Substance - what a comment earns its place

- Comment the why, never the what. Restating the code is a defect; delete such
  comments.
- A comment must add at least one of: why this exists; why this way and not the
  obvious way; an invariant the reader must not break; a non-local consequence
  or edge case; a requirement change that makes the code look wrong on first
  read.
- If deleting it loses no decision context, delete it. No decorative comments,
  no commented-out code.

## Form - same decisions, native expression

- File header, one per file: line 1 is `name - one-line purpose.`; blank line;
  up to ~4 lines of what/why/how (flow, invariants); the usage or run command
  when there is one.
- Doc comment on public symbols only when the contract is not fully derivable
  from name + signature: edge cases, side effects, constraints. Otherwise the
  name is the documentation.
- Logic comment placement: own-line when it explains a block's why, runs more
  than one clause, or would push the line past the project's line budget;
  inline (trailing) when it clarifies one specific token or edge on that exact
  line in a short clause.
- Section banner only in files with 3+ sections or more than ~120 lines: two
  divider lines of exactly 78 chars (`// ` + 75 dashes) with the section name
  between them.
- TODO/FIXME only with what is deferred and why attached; bare ones are banned.

## Never

- Restate the code, state the obvious, credit authorship or dates (git blame
  exists), comment out code, leave a bare TODO/FIXME.

## Check your diff

- Any comment that restates code, or any header missing its purpose line?
- Any comment left stale by your edit (old reason, new code)?
- Any decorative comment that loses no decision context if deleted?

## Example

```
count += 1; // increments count        <- restates the code: delete it
count += 1; // keep v1 rows 30d longer  <- why, from a changed requirement
```
